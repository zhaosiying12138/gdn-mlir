## 九、可复现性的工程学：种子、限额与逐字节一致

编译期调度拿走了运行时 autotune 的工作，就必须提供 autotune 给不了的东西：决策过程可重放、决策产物可存档。运行时搜索的每一次结果都取决于当时的机器状态与竞争负载；编译期求解的每一次结果都应当取决于且仅取决于输入。求解器的确定性控制面由种子、资源限额与四道顺序纪律构成，它们让两次运行逐字节一致、让排名文件成为可存档、可 diff、可在持续集成里断言的证据。

术语先立。随机种子（seed）固定伪随机数序列的起点；rlimit 是 z3 的资源计量上限；逐字节一致指两次运行的全部输出文件在字节层面完全相同，diff 为空。

### 1. 控制面：种子与限额的设置

z3 求解器内部有启发式分支决策，两个参数把它钉成确定状态：

```
DEFAULT_SEED = 7                 # fixed (determinism)
DEFAULT_RLIMIT = 20_000_000      # cap solver effort (determinism)
...
s = z3.Solver()
# z3 5.1.0: the solver seed parameter is `random_seed`
s.set("random_seed", seed)
s.set("rlimit", rlimit)
```

random_seed 固定分支启发式的伪随机源；源码注释专门记录了 z3 5.1.0 的参数名拼写，这类版本细节正是复现时的暗礁。rlimit 给求解工作量设上限，它的语义见第三节。两个默认值作为模块常量存在，调用方不改。docstring 的确定性条款还有一句总纲：No RNG anywhere else（22 行）——求解器之外的代码不存在任何随机源，整条链上没有第二个需要固定的随机状态。

### 2. rlimit 的语义：确定性的资源计量

rlimit 计量求解器内部的资源单位——分支、传播等操作的加权计数，同一问题每执行一次消耗同样的单位。这使它与墙钟超时有本质差别：墙钟随机器与负载漂移，同一问题在不同机器上可能一次穷尽一次截断；rlimit 与机器无关，同一问题、同一种子、同一限额，两次运行要么都干净穷尽，要么在同一决策点停下。限额因此同时兑现两件事。

其一，截断可检测。限额耗尽时 check 返回 unknown，与"证明无解"的 unsat 是不同的返回值——第八章的防御正是靠这个区分，把截断空间拦在产出之前；输出里的 last_check 字段让复核者看到枚举究竟以哪种方式结束。其二，截断可复现。即使截断发生，两次运行也截在同一处；解除限额重试的结果同样确定（重试标志 rlimit_retry_uncapped 随输出落盘）。限额值取 2×10⁷，对这两个空间绰绰有余（0.29 与 0.33 秒穷尽 368 与 465 个配置），无上限重试路径作为保险丝存在。一句话概括设计意图：限额是一道确定性的闸，关上时行为可预期，必要时可整体拆除重跑。

### 3. 四道顺序纪律

种子只固定求解器内部的随机性，输出的顺序还依赖四道显式纪律。

表 26-1：确定性控制面的四道顺序纪律
| 纪律 | 固定的对象 | 出处与消费处 |
|---|---|---|
| 变量声明序 | self.v 字典十个键的登记顺序 | 98-110 行声明；模型读取、补全遍历、阻塞子句构造都按它 |
| 域序 | domains 各元组的候选排列 | 168-173 行；补全探测按序取第一个合法候选 |
| 阻塞子句序 | 每轮阻塞项的构造与叠加顺序 | 254-257 行；求解器行为依赖断言集内容与顺序 |
| 终排序键 | 预测毫秒四舍五入到十二位小数，并列按配置名 | 393 行；输出清单与模型产出顺序解耦 |

四道纪律的合力可以这样读：求解器每次 check 面对同一棵搜索树（种子加断言序固定），产出的解序列一致；解序列再经固定的补全顺序与固定的排序键重排，输出清单逐项一致。任何一个环境变量、任何一个字典遍历顺序的偶然变化，都会在第一时间表现为两次运行输出文件的 diff——可复现性因此本身就是一道回归检测。

### 4. 逐字节一致的验证与排名作为证据

验证方式是直接的：同一命令行运行两次，对输出 JSON 做字节级比较，diff 为空即通过。第三十六章记录的结果即由这条控制面保证：Z3 固定声明序、种子 7、资源上限 2×10⁷，两次完整编译逐字节一致；生成器同种子两次生成的 MLIR 哈希相同；全部旋钮关断时产物与默认配置逐字节等价（27 份 payload、18 个 cubin）。输出 JSON 同时是它自己确定性配置的说明书——z3 字段落盘 seed、rlimit、last_check、rlimit_retry_uncapped 与 enum_stats（403-406 行），复核者拿到一份排名文件，就同时拿到了产出它的全部确定性参数。

求解器只是编译端确定性工程的一环，同一原则在两侧延伸。编译端上游：生成器产物走 MLIR 哈希比对；PTX 后处理的缓存键取全部旋钮环境变量加源码指纹的哈希，键不匹配时缓存自动失效——缓存命中与重新计算不产生分歧。运行端：同一 cubin、同一输入、同一发射几何下输出逐位一致，跨进程（全新 CUDA 上下文与模块加载）验证五次全过方为通过；该协议抓到过五个真实竞态，全部在数值容差之内——数值验证对这类缺陷无感，逐位一致性是唯一能抓到它们的尺子（第三十六章）。两侧合起来，"确定性"在本项目里是一个可检验的合同，从求解器的种子一路贯穿到设备上的输出字节。

排名文件由此获得三重身份。可存档：它是文本，随证据树归档，第几次运行、哪年哪月产出都以字节固定。可 diff：两次运行逐字节一致，约束或成本模型的任何改动都会表现为排名文件里的可见行——哪个配置升了、哪个降了、空间尺寸变没变，一目了然。CI 可断言：持续集成重跑求解并比对输出哈希，"调度决策漂移"从一句担忧变成一个红绿灯；排序质量门槛（Spearman 不低于 0.7）同样可以从 validate 报告直接断言。

这正对应第一章表 1 的第二支柱（编译期确定性调度）：从约束模型、枚举清单、排名到 transform 工件，调度决策的全链由文本中介。一份调度决策因此可以像源代码一样被引用、评审、质疑与回滚——第四章的两问（凭什么排序、凭什么相信）最终落在这份可复现的证据文件上。
