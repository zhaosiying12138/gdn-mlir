# G5-A Baseline Report — fla / FlashQLA baselines + JAX fp64 reference data

Workstream G5-A, 2026-10-09.  All timings on **RTX 5090 Laptop (sm_120, 82 SMs,
99KB/CTA smem opt-in)** in an *opportunistic shared window* (co-job pid 3411456,
~17.9GB resident): absolute times are noisy by design; medians of >=50
CUDA-event reps after >=10 warmups.  Register rows: `~/codebase/GPU-COORDINATION.md`
(session `gdn-mlir`, task `G5 baselines`, `<4GB`, opportunistic).

Shapes (docs/PLAN.md G5): **B1T2048 / B1T8192 / B4T2048, H=HV=16, K=V=128**,
bf16 io (q/k/v/do bf16; beta/g/h0/dht fp32, per fla `test_chunk`), scale=K**-0.5,
`output_final_state=True`, q/k l2-normalized outside the op.  Inputs are
generated by the shared module `tools/gdn_bench_common.py` (fla
`tests/ops/test_gdn.py::test_chunk` recipe, seed 42) — the **same tensors**
feed the fla harness, the FlashQLA harness and the JAX fp64 reference, so every
number below is directly comparable.

## 1. fla `chunk_gated_delta_rule` baselines

(mode, shape) because fla caches the backend decision per process
(`BaseBackend.can_use` is `@cache`).

| B4T2048 | triton (`FLA_FLASH_QLA=0`) | **0.844 ms** | 0.809 ms | **3.873 ms** | 3.433 ms | 1009 MB |

**口径 verification (backend probe, recorded per run in the JSON):**
`FLA_FLASH_QLA=0` provably disables the FlashQLA/TileLang backend
(`FlashQLABackend.is_enabled()=False, can_use()=False`).  In the `default`

is not installed in env `gdn`, so **on this box default dispatch resolves to
the same Triton path**; the two modes agree within shared-window noise
(B1T2048 fwd 0.316 vs 0.347 ms etc.).  The genuine FlashQLA-dispatch fwd
number is the direct-call measurement below (env `gdn-tl`).

## 2. FlashQLA (TileLang) forward

Harness: `tools/gdn_bench_flashqlaptx.py` (env `gdn-tl`: tilelang 0.1.15,
torch 2.14.1+cu130, flash_qla editable @ `~/codebase/FlashQLA`).  SM120 ships
a bf16 **forward-only** kernel (chunk_size=32; no backward) — fwd-only timing.

| shape | fwd median | fwd min | vs fla triton fwd | auto_cp | block_DV | peak |
|---|---|---|---|---|---|---|
| B1T2048 | **0.139 ms** | 0.131 ms | **2.27x** | True (intra-CP) | 64 | 62 MB |
| B1T8192 | **0.404 ms** | 0.389 ms | **2.16x** | True (intra-CP) | 64 | 222 MB |
| B4T2048 | **0.355 ms** | 0.350 ms | **2.38x** | n/a (B>1 dense) | 64 | 218 MB |

**Two sm120 launchability findings (both disclosed in `flashqla_fwd.json`,
neither is a patch to the FlashQLA repo):**

1. *Upstream export bug:* `chunk/cp/preprocess.py::cp_preprocess_fwd/bwd`
   import `aggregate_card_state` from `flash_qla...chunk`, which the sm120
   branch of `chunk/__init__.py` deliberately does not export (it exists only
   for SM90/SM100 inter+intra CP).  Every public sm120 call raises
   `ImportError`.  The harness injects `aggregate_card_state = None` at runtime
   (the documented sm120 semantics; `_assert_inter_intra_supported` accepts
   `None` for pure-intra/pure-inter).
2. *smem overflow under tilelang 0.1.15:* the shipped `block_DV=128` fwd
   kernel requests **112,640 B** dynamic smem > the sm120 opt-in limit
   **101,376 B (99KB)** and cannot launch (TVM `InternalError`), in both the
   dense and the intra-CP layout.  Upstream's own 5090 results
   (`FlashQLA/benchmark/benchmark_results_5090.txt`) were measured with
   tilelang **0.1.13**.  The harness falls back to the kernel's **own
   `block_DV` parameter forced to 64** (~77KB, launches), recorded as
   `fwd_block_dv=64`; outputs are finite and cross-checked against fla Triton
   fwd on the same inputs (section 4).

Upstream context (not ours, different shapes GVA h_qk=2/h_v=8, cudagraph
backend, tilelang 0.1.13): FlashQLA fwd 0.076 ms @ 1x2048, 0.186 ms @ 1x8192,
1.3-1.8x faster than fla fwd there — consistent in direction with our 2.2x
(H=16 flat, no cudagraph, shared window).

## 4. JAX fp64 reference data + fla tolerance calibration

`tools/gdn_e2e_ref.py` (env `gdn`, jax 0.11.2 CPU, fp64, chunk_size=64):
generates inputs with the shared recipe, runs `tools/gdn_ref_jax.py`
`gdn_chunk`/`gdn_chunk_vjp` on the exact bf16 values the GPU sees, dumps
refs (f64/f32/bf16 casts; the bench-case npz ships f32/bf16 + fla outputs,
f64 columns kept only for the small case — regenerable deterministically in
~40 s via the script) + fla Triton outputs (fwd + autograd.grad) for the
same tensors.  Spec self-check: chunk-vs-sequential fp64 max|Δ| ≤ 1e-14 on
the small case (all 8 outputs).

T8192 fp64 refs are intentionally skipped (CPU cost); numerics interpolate
via the T512/T2048 cross-checks — the per-chunk kernels are identical, only
the chunk count changes.
